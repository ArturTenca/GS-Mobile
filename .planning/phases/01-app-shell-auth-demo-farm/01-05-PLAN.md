<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input -> auth forms | Untrusted strings (name, e-mail, password) |
| app -> Supabase Auth | Credentials in transit over HTTPS |
| device storage -> session | Tokens persisted in SQLite-backed localStorage / browser localStorage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Spoofing | Login brute force | mitigate | Client cooldown (5 failures -> 30s, UX only) plus Supabase server-side auth rate limits as the real defense (A3: verify in dashboard) |
| T-05-02 | Information disclosure | Account enumeration via login/reset messages | mitigate | Generic "E-mail ou senha inválidos."; reset always reports sent (resetPassword returns null error) |
| T-05-03 | Tampering | Malformed/control-character input | mitigate | `sanitizeEmailInput`/`sanitizePasswordInput`/`sanitizeTextField` on change; `validate*` on submit; length caps; DB check constraints (plan 02) |
| T-05-04 | Information disclosure | Error text/log leakage | mitigate | `mapAuthError` returns fixed PT-BR strings; `console.error` logs fixed strings only, never error objects |
| T-05-05 | Information disclosure | Secrets in bundle | mitigate | Only `EXPO_PUBLIC_SUPABASE_URL`/`ANON_KEY` read; grep gate for `service_role`; `.env` ignored |
| T-05-06 | Elevation of privilege | Client route guard bypass | accept | Stack.Protected is UX only; RLS per owner (plan 02) is the enforcement |
| T-05-07 | Spoofing | Session theft from storage | accept | Standard supabase-js + expo-sqlite storage per Expo/Supabase docs; short-lived JWT with refresh rotation |
</threat_model>
