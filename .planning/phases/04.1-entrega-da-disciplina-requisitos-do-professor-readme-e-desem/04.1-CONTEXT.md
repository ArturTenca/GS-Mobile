<decisions>
## Implementation Decisions

### Grading criteria (all locked — each must be demonstrably satisfied)
- D-01 Telas e navegação: Expo Router app with clear, working navigation between the main screens (tabs + detail + flows); no dead ends or stub screens reachable from navigation.
- D-02 Consumo de dados: the app consumes data from an API or a mock (Open-Meteo forecast already exists; Supabase REST/RPC is also API consumption). Loading, error and empty states must be visible and handled.
- D-03 Banco de dados: the app saves information to a database (Supabase Postgres: farms, sensors, thresholds, alert status, notification prefs). At least one citizen-facing "registrar" flow must write and read back data end to end.
- D-04 Acessibilidade: simple and accessible for non-specialists — accessibilityLabel/role on interactive elements, min 48dp targets, readable contrast, font scaling not breaking layouts, plain pt-BR copy.
- D-05 Aderência ao problema: the app resolves the citizen's main journey defined in the Ficha (consultar, registrar, receber informação) — for AgroAlerta: see farm status, register farm/sensor/limits, receive alerts.
- D-06 Documentação: README.md at repo root with (a) Ficha da CitizenTech section, (b) instruções para rodar (requirements, .env, Supabase SQL setup, npm/expo commands, web and phone), (c) prints das telas, (d) link do vídeo de até 3 min.

### Entregáveis
- D-07 Repository code organized (existing modular structure; remove leftovers/dead files that confuse a grader, keep `.env` out of git, provide `.env.example`).
- D-08 README includes video link placeholder + 3-minute video script; screenshots folder (e.g. `docs/prints/`) referenced from README. Screens/video are captured by a human — plan a human checkpoint to drop the files in.
- D-09 Ficha da CitizenTech content is not in the repo: README section is pre-filled from .planning/PROJECT.md and clearly marks fields the team must confirm.

### Performance (user requirement)
- D-10 App must open and show content quickly and feel light: measure and cut startup/bundle cost (lazy-load heavy screens/libs such as map/WebView and charts, avoid blocking work on startup, avoid unnecessary network waterfalls, sensible React Query staleTime/caching, splash kept only until essentials are ready). Provide a measurable before/after (e.g. web bundle size, number of startup requests, time to first content) recorded in the SUMMARY.

### Claude's Discretion
- How to measure performance (export bundle analysis, timing logs) and which optimizations give the biggest win.
- README structure and wording beyond the required sections (pt-BR).
- Specific accessibility fixes after the audit.
- Whether gaps are fixed in this phase or explicitly noted as covered by Phase 4 (in progress).

</decisions>
