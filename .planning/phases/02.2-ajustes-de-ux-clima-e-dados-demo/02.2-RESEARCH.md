# Phase 2.2: Ajustes de UX, clima e dados demo - Research

**Researched:** 2026-11-12
**Domain:** Expo/RN-Web UI settings + popups, Open-Meteo forecast, monochrome Leaflet map, gifted-charts line charts, Supabase demo-dataset RPC
**Confidence:** MEDIUM-HIGH (API and tile behavior verified live; chart rendering on RN Web and WebView CSS filter need on-device visual check)

## Summary

Five independent slices on top of Phase 2.1. Four are low risk and mostly local code: a persisted `preferences` store plus ThemeProvider (PRF-06), unified centered popups (UX-01), the Open-Meteo adapter plus a pure WMO mapper (WX-01), and the history service plus chart cards (ANL-01). The migration 007 RPC (DEMO-02) is mostly a refactor of the 006 generator.

Two findings change the CONTEXT's assumptions. (1) **CARTO `light_all`/`dark_all` raster tiles no longer work without an API key.** Since 2026-09-25 they return an "API KEY REQUIRED" watermark tile (verified by fetching a tile). A key is free but would be embedded in a public client and needs a registration the user has not done. D-10's preferred option is therefore not viable under the project's "no API keys" tile rule, so use its fallback: the existing OSM / Esri tiles with a CSS `filter` on the Leaflet tile pane, driven by a `theme` field in the scene. (2) **`localStorage` on native only exists because `src/lib/supabase.ts` imports `expo-sqlite/localStorage/install`.** The `selectedFarm` adapter picks `localStorage` at store-creation time, so it silently degrades to an in-memory Map on native if the store module is evaluated before supabase.ts. The new preferences store must import the install shim itself through a shared adapter, or the theme choice will not survive an app restart on phones.

Further traps found: PostgREST caps responses at 1000 rows by default (30 days of hourly readings is 721 rows per sensor, so query per sensor, never `.in(sensor_ids)` for the whole farm); the 006 `register_sensor` already inserts 30 days of demo readings, so "no data yet" is not what `demo_data_generated_at is null` means; and `react-native-gifted-charts` is not installed (1.4.81 is current, it needs `expo-linear-gradient` only for gradient or area fills).

**Primary recommendation:** Build in this order: shared persist adapter + preferences store + ThemeProvider; Modal `scroll` mode + ConfirmDialog and migrate Select/FarmSelector; weather service/mapper/card; scene `theme` + CSS filter on OSM/Esri tiles; migration 007 (shared generator) followed by the readings/thresholds services and chart cards. Treat the user applying 007 as a [BLOCKING] checkpoint before the Análises plan is verified.

### Pattern 1: Open-Meteo request and response (verified live 2026-11-12)
**Request** (CORS: `access-control-allow-origin: *`; rate headers `X-RateLimit-Limit: 600`/min):
```
GET https://api.open-meteo.com/v1/forecast?latitude=-23.55&longitude=-46.63
  &current=temperature_2m,relative_humidity_2m,weather_code,wind_speed_10m,precipitation
  &daily=weather_code,temperature_2m_max,temperature_2m_min,precipitation_probability_max
  &timezone=auto&forecast_days=7
```
**Response shape (actual):**
```json
{ "latitude": -23.51, "longitude": -46.61, "utc_offset_seconds": -10800, "timezone": "America/Sao_Paulo",
  "current_units": { "temperature_2m": "°C", "relative_humidity_2m": "%", "weather_code": "wmo code", "wind_speed_10m": "km/h", "precipitation": "mm" },
  "current": { "time": "2026-11-12T17:30", "interval": 900, "temperature_2m": 22.2, "relative_humidity_2m": 81, "weather_code": 3, "wind_speed_10m": 5.8, "precipitation": 0.0 },
  "daily_units": { "...": "..." },
  "daily": { "time": ["2026-11-12", "..."], "weather_code": [95, 95, 3, 95, 51, 80, 95],
             "temperature_2m_max": [25.8], "temperature_2m_min": [16.7], "precipitation_probability_max": [100] } }
```
Errors are HTTP 400 `{"error": true, "reason": "..."}`. `daily.time[0]` is the farm's local "today" because of `timezone=auto`.

Adapter rules (`weather.ts`): build URL with `URLSearchParams`; round coords to 2 decimals (also the query key); `AbortController` timeout ~8 s; `res.ok` check; validate that every `daily` array has the same length as `daily.time` and numbers are finite (`precipitation_probability_max` entries may be `null`: map to `null`); wrap everything in `ServiceError('Não foi possível carregar a previsão.')`. Always request Celsius and km/h; convert in the UI.

### Pattern 3: Monochrome themed map (CSS filter, no keys)
Verified: `a.basemaps.cartocdn.com/light_all/{z}/{x}/{y}.png` and `/rastertiles/light_all/...` both return the "API KEY REQUIRED, carto.com/basemaps/apikey" watermark tile on 2026-11-12 (CARTO FAQ: keys required since 2026-09-25; free up to 5M requests/month non-commercial and 1M commercial; attribution mandatory) [CITED: docs.carto.com/faqs/carto-basemaps].

Recommendation: keep `TILE_LAYERS.street` (OSM) and `.satellite` (Esri); add `theme: 'light' | 'dark'` to `MapScene` (not part of `rev`, so a theme switch never re-fits the view) and apply the filter to the **tile pane element** (one composited layer, avoids seams that per-`<img>` filters can show). Overlays (polygon, circles, markers) live in other panes and stay colored.
```js
// in PAGE_SCRIPT apply(s): 
document.documentElement.setAttribute('data-theme', s.theme === 'dark' ? 'dark' : 'light');
var pane = map.getPane('tilePane'); pane.className = 'leaflet-pane leaflet-tile-pane base-' + s.base;
document.body.style.background = s.style.mapBackground; // token for the not-yet-loaded tiles
```
```css
/* in the <style> block of buildMapHtml (inline style already allowed by the CSP) */
.base-street { filter: grayscale(1) contrast(.95) brightness(1.04); }
html[data-theme="dark"] .base-street { filter: grayscale(1) invert(1) brightness(.82) contrast(.9); }
.base-satellite { filter: grayscale(1) contrast(.95); }
html[data-theme="dark"] .base-satellite { filter: grayscale(1) brightness(.7) contrast(1.05); }
```
Starting values; tune visually against `colors.background` for both themes. Add `theme` and `mapBackground` (new token) to the scene builder in `mapProtocol.ts`/`sceneStyleFromColors`; callers pass `useTheme().theme`. Because the HTML is built once (`useMemo(() => buildMapHtml(), [])`) and the scene is re-posted whenever it changes, theme flips update live on web and native with no remount. CSP needs no change (no new tile hosts, no new connect-src). Default `useState<MapBase>('street')` in `FarmMapStep` and `SensorMapStep` (currently `'satellite'`); `MapLayerToggle` labels become "Mapa" / "Satélite" (key `street` stays to avoid churn). Attribution stays on the map (OSM text already; keep Esri text for satellite).

Caveat [ASSUMED]: CSS `filter` support in react-native-webview (Android WebView and iOS WKWebView are Chromium/WebKit and both support it), not testable here; verify on a device. Invert of dark-mode OSM tiles yields light roads on dark grey, which is the intended look.

### Pattern 4: Persisted preferences without a flash
```ts
// src/stores/persistStorage.ts
import 'expo-sqlite/localStorage/install'; // defines global localStorage on native; no-op on web
import { createJSONStorage, type StateStorage } from 'zustand/middleware';
const memory = new Map<string, string>();
const memoryStorage: StateStorage = { getItem: (k) => memory.get(k) ?? null, setItem: (k, v) => { memory.set(k, v); }, removeItem: (k) => { memory.delete(k); } };
export const persistStorage = createJSONStorage(() => (typeof localStorage !== 'undefined' ? localStorage : memoryStorage));
```
Refactor `selectedFarm.ts` to use it too (same behavior, removes the import-order hazard). `localStorage` (web and the expo-sqlite shim) is synchronous, so zustand `persist` hydrates synchronously at store creation and the very first ThemeProvider render already has the saved theme: no in-app flash. Store:
```ts

### Pattern 6: Charts with gifted-charts on RN Web
Props confirmed from `gifted-charts-core@0.1.83` type definitions [VERIFIED: package tarball]: `data`, `width`, `height`, `spacing`, `initialSpacing`, `endSpacing`, `adjustToWidth`, `parentWidth`, `disableScroll`, `maxValue`, `mostNegativeValue`, `yAxisOffset`, `noOfSections`, `hideDataPoints`, `dataPointsRadius`, `areaChart`, `isAnimated`, `animateOnDataChange`, `rulesType`, `yAxisLabelWidth`, `hideYAxisText`, `formatYLabel`, `xAxisLabelTexts`, `showReferenceLine1..3`, `referenceLine1..3Position`, `referenceLine1..3Config` (`{ thickness, width, color, type, dashWidth, dashGap, labelText, labelTextStyle, zIndex }`), `referenceLinesOverChartContent`, `pointerConfig`, `scrollToEnd`.

Recommended usage:
- Measure the card with `onLayout`; compute `chartWidth = cardInnerWidth - yAxisLabelWidth(36)`; pass `width={chartWidth}`, `disableScroll`, `initialSpacing={0}`, `endSpacing={0}`, `spacing = chartWidth / Math.max(1, data.length - 1)`, `hideDataPoints`, `isAnimated={false}`, `thickness={2}`. - Thresholds: `showReferenceLine1` at `max_value` and `showReferenceLine2` at `min_value` with dashed `referenceLineNConfig` colors from tokens (warning/critical) and `labelText`.
- Avoid `yAxisOffset` (its interaction with `maxValue` and reference-line positions is unverified: LOW). Use a 0-based axis: `maxValue = niceCeil(max(dataMax, thresholdMax) * 1.1)`, `noOfSections = 4`. Humidity/soil are 0-100%, temperature fits 0-40 °C; for °F convert first and compute the domain after conversion. Put this in a pure `chartDomain()`.
- Points: 24 h = 24 raw hourly points; 7 d = 168 raw, downsample to 2 h buckets (84); 30 d = 721 raw, 6 h buckets (about 120). Stats (min, max, mean, latest) are computed from the raw series, not the buckets. X-axis labels only every ~Nth point via data-item `label` (HH:mm for 24 h, weekday for 7 d, dd/MM for 30 d) using device-local time; `labelTextStyle` color from tokens.
- Memoize the data array and wrap the card in `React.memo`; render cards independently so one loading sensor does not block others. Up to 30 SVG charts of ≤120 points each is fine on web; consider rendering cards in a `FlatList`/lazy mount only if profiling shows jank.
- Accessibility: set an `accessibilityLabel` on the chart wrapper in PT-BR ("Gráfico de {nome}, mínimo X, máximo Y, média Z no período") and do not rely on color alone for threshold state (label text next to the lines).

### Pattern 7: Migration 007 (shared generator, RPC)

create or replace function private.generate_sensor_readings(
  p_sensor uuid, p_property uuid, p_type public.sensor_type, p_start timestamptz, p_end timestamptz)
returns integer language plpgsql security definer set search_path = '' as $$
declare v_seed int := abs(hashtext(p_sensor::text)) % 1000; v_n int;
begin
  insert into public.readings (sensor_id, property_id, recorded_at, value, is_demo)
  select p_sensor, p_property, pts.ts,
    round((
      case p_type
        when 'temperature'  then 24 + 5 * sin(2*pi()*(pts.hr-9)/24.0)
        when 'air_humidity' then 70 - 12 * sin(2*pi()*(pts.hr-9)/24.0)
        else 58 - 4 * ((pts.h/24.0) - 5 * floor(pts.h/120.0)) end
      + 0.4*sin(pts.h*1.7 + v_seed*3.1) + 0.3*sin(pts.h*0.53 + v_seed)
      -- excursions so charts show warnings (defaults: temp 10-32, humidity 30-85, soil 25-80):
      + case when floor(pts.h/24) % 9 = v_seed % 9 and pts.hr between 13 and 16 then
          case p_type when 'temperature' then 9 when 'air_humidity' then 0 else -22 end else 0 end
      + case when p_type = 'air_humidity' and floor(pts.h/24) % 11 = v_seed % 11 and pts.hr between 2 and 6 then 14 else 0 end
    )::numeric, 1), true
  from (select g.ts, extract(epoch from (g.ts - p_start))/3600.0 as h,
               extract(hour from (g.ts at time zone 'America/Sao_Paulo')) as hr
        from generate_series(p_start, p_end, interval '1 hour') g(ts)) pts;
  get diagnostics v_n = row_count;
  update public.sensors set last_seen_at = p_end where id = p_sensor;
  return v_n;
end $$;
revoke all on function private.generate_sensor_readings(uuid, uuid, public.sensor_type, timestamptz, timestamptz) from public, anon, authenticated;

create or replace function public.generate_demo_dataset(p_property_id uuid)
returns jsonb language plpgsql security definer set search_path = '' as $$
declare v_uid uuid := (select auth.uid()); v_last timestamptz; v_end timestamptz := date_trunc('hour', now());
        v_s record; v_sensors int := 0; v_rows int := 0;
begin
  if v_uid is null then raise exception 'not authenticated' using errcode = '42501'; end if;
  select p.demo_data_generated_at into v_last from public.properties p
   where p.id = p_property_id and p.owner_id = v_uid for update;       -- ownership + row lock (serializes double taps)
  if not found then raise exception 'Fazenda nao encontrada.' using errcode = '42501'; end if;
  if v_last is not null and v_last > now() - interval '1 minute' then
    raise exception 'Aguarde um minuto para gerar os dados de novo.' using errcode = 'AG429'; end if;
  delete from public.readings r using public.sensors s
   where r.sensor_id = s.id and s.property_id = p_property_id and r.is_demo;  -- real readings untouched
  for v_s in select id, type from public.sensors where property_id = p_property_id loop
    v_rows := v_rows + private.generate_sensor_readings(v_s.id, p_property_id, v_s.type, v_end - interval '30 days', v_end);
    v_sensors := v_sensors + 1;
  end loop;
  update public.properties set demo_data_generated_at = now() where id = p_property_id;
  return jsonb_build_object('sensors', v_sensors, 'readings', v_rows, 'generated_at', now());
end $$;
revoke all on function public.generate_demo_dataset(uuid) from public, anon;
grant execute on function public.generate_demo_dataset(uuid) to authenticated;
```

### Pattern 8: History queries and demo time anchoring
- Index: `readings_sensor_time_idx (sensor_id, recorded_at desc)` serves `where sensor_id = $1 and recorded_at >= $2 order by recorded_at`. No new index needed.
- PostgREST row cap: default `max-rows` is 1000. A single sensor over 30 d at hourly resolution is 721 rows, so `readings.ts` queries **per sensor** (`.eq('sensor_id', id).gte('recorded_at', since).order('recorded_at', { ascending: true }).limit(1000)`) inside `useSensorHistory(sensorId, period, offsetMs)`; do not use `.in('sensor_id', allIds)`. Real sensors with sub-hourly data are a Phase 3 problem (note it in the service).
- Anchoring (Phase 2 D-08): readings carry `is_demo`. Fetch the farm's latest demo timestamp once (`latest_readings` view filtered by `is_demo`, one row per sensor), compute `offset = computeDemoOffset(maxDemoTs, now)` via the existing helper, query `since = now - periodMs - offset`, and map rows with `shiftDemoRow`. Freshly generated data ends at the top of the hour, so the offset is at most about an hour and the clamp in `shiftTs` keeps the last point at or before now. The offset hook `useDemoOffset(propertyId)` should share the `['home']`/`['readings']` invalidation family so regeneration refreshes it.
- Thresholds: new `thresholds.ts` (`select sensor_type,min_value,max_value where property_id`), `numeric` arrives as string or number, so coerce with the same `num()` helper pattern as `sensors.ts`.
- After generation `useGenerateDemoData` invalidates `['sensors']`, `['home']`, `['farms']` (carries `demo_data_generated_at`), and `['readings']` (use this prefix for history/offset keys, scoped by userId like the existing hooks).
- `Property` type: add `demo_data_generated_at?: string | null` (undefined before 007 is applied counts as null).
- Gating: `useEffect` once per screen mount (ref flag) when farms and sensors are loaded, `sensors.length > 0 && !farm.demo_data_generated_at`; "Agora não" only closes. Because `register_sensor` already writes 30 days of demo readings for each new sensor, charts may already have data when the prompt shows; every sensor card must therefore also handle "Sem leituras neste período" (empty state), not assume the dataset exists.

## Common Pitfalls

### Pitfall 1: Theme lost on native restart
**What goes wrong:** Preference resets to system after relaunch. **Why:** `localStorage` global only exists after `expo-sqlite/localStorage/install`; module order decides. **Avoid:** shared `persistStorage` importing the install shim. **Warning sign:** works on web, not on device.

### Pitfall 2: CARTO watermark tiles
**Avoid:** OSM/Esri + CSS filter. **Warning sign:** "API KEY REQUIRED" diagonal text on tiles.

### Pitfall 3: Chart overflow or mid-chart clipping at 360 px
**Avoid:** explicit `width` from `onLayout`, `disableScroll`, computed `spacing`, `initialSpacing/endSpacing = 0`. Verify at 360 px and a 1280 px browser window.

### Pitfall 4: Truncated history
1000-row PostgREST cap. Query per sensor, cap `limit(1000)`, test with 30 d.

### Pitfall 5: Popup wider than content on web
RN Web `Modal` ignores the app column. Keep `width: '100%'` + `maxWidth: 400` on the panel itself; never `flex: 1` the panel; no `justifyContent: 'flex-end'` backdrop.

### Pitfall 6: Weather for farms without coordinates
`center_lat/center_lng` are null on legacy/demo farms. The hook must be `enabled` only when both exist; show the D-08 fallback. Do not send `null` coordinates (API returns 400).

### Pitfall 7: °F applied twice or not to thresholds
Convert at the presentation edge once (values, domain, reference lines, labels). Keep stored data and queries in Celsius.

### Pitfall 8: Regenerating wipes the legacy seeded demo farm's data
Acceptable but the confirm copy should say existing demo readings are replaced.

### Pitfall 9: Double tap on "Gerar dados"
Disable button while mutating; server row lock + 1-minute throttle protect anyway.

### Bucket downsampling (pure)
```ts
export function downsample(points: { t: number; v: number }[], bucketMs: number) {
  const out: { t: number; v: number }[] = [];
  let key = -1, sum = 0, n = 0, t0 = 0;
  for (const p of points) {
    const k = Math.floor(p.t / bucketMs);
    if (k !== key) { if (n) out.push({ t: t0, v: sum / n }); key = k; sum = 0; n = 0; t0 = p.t; }
    sum += p.v; n++;
  }
  if (n) out.push({ t: t0, v: sum / n });
  return out;
}
```
